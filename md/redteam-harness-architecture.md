# Красный харнесс: архитектура под семь требований

Как Samurai AI закрывает требования к лучшему Red Team Harness. Каждое
требование — с тем, что уже есть в коде (со ссылками на FR), и чего не хватает.

## Принцип

Харнесс вокруг любой LLM = модель никогда не держит ни состояние, ни границы,
ни методологию в своей голове. Модель предлагает; харнесс помнит, проверяет,
разрешает и судит. Любая LLM (локальная, фронтирная, через relay) встречает
один и тот же контур: blackboard + события + контракт скоупа + судьи.

## 1. Методология атак

- Есть: гены (`agents/genes`), плейбуки (`PlaybookService`, FR-18), память
  кампании (FR-17), доктрина в промптах (FR-107), специализации
  (recon/testing/analysis/strategist, FR-105).
- Добавить: методологический бэкбон как данные — стадии × типы поверхности ×
  техники (PTES/ATT&CK kill chain как проверяемый чек-лист покрытия), откуда
  генератор гипотез черпает «что ещё не пробовали».

## 2. Kill chain из задачи, управляемый и корректируемый

- Есть: рельс стадий (FR-99) — двигается по задачам, фактам, интентам и
  лестнице импакта; цель с судьёй (FR-112).
- Добавить: kill chain как **управляемый объект**, а не отображение:
  - переход стадии — событие; на нём стратег пересматривает вектора
    (fact.confirmed → стратег: «что это открывает»);
  - стадия имеет критерии выхода (что должно быть доказано, чтобы двинуться
    дальше), не только маркеры текста;
  - тупик стадии (N попыток без факта) — тоже событие: перепланирование, а не
    застревание.

## 3. Все гипотезы, отранжированные по вероятности

- Есть: домен гипотез (open→testing→confirmed/refuted), стратег
  (propose_hypothesis, FR-105), доска «Ход».
- Добавить:
  - генератор покрытия: из методологического бэкбона + карты поверхности
    (найденные сервисы/версии/эндпоинты) строится полный набор гипотез
    («для Go text/template: SSTI; для n8n на хосте: API abuse; …»);
  - ранжирование: prior по методологии (частотность класса) × свидетельства
    (каждый факт двигает вероятность), пересчёт на каждом событии;
  - бюджет работы идёт в гипотезу с максимальным expected value, а не по
    порядку списка.

## 4. Постоянный контроль и валидация

- Есть: судья цели на завершении (FR-112), гейт свидетельств (FR-93),
  scope-гард по токенам (FR-113), брейкер процессов, детекторы
  стагнации/дрейфа/обещаний (FR-108/110).
- Добавить:
  - ре-валидация находок по расписанию/по событию (находка старше N шагов и
    не подтверждалась → retest);
  - сторож стадии: стадия без продвижения X минут при активных шагах —
    эскалация стратегу;
  - контроль бюджета как приборная панель (шаги/время/деньги против цели).

## 5. Агент-исследователь

- Есть: `research.search`/`research.read` (FR-57), intel.* (FR-82), память.
- Добавить: специализация `researcher`: по событию «новый сервис/версия/
  технология» — автоматический поиск (CVE, техника, публичные эксплойты),
  результат — гипотезы стратегу через blackboard. Не исполняет, только
  докладывает координатору.

## 6. TUI

- Есть: SCOPE (цели со статусом), LOOT (+флаги), рельс, шкала контекста
  ⇈/⇊, вкладки, доски.
- Добавить: рельс с критериями выхода по стадиям (что осталось доказать),
  доска гипотез с вероятностями (сортировка по ним), счётчик покрытия
  методологии («покрыто 14/22 векторов поверхности»).

## 7. Лучший в мире — измеримо

- Live-eval сценарии (evals/): Takeoff как эталон — user.txt за N шагов,
  ≤10% провалов, ноль провалов транспорта. Набор боксов по сложности
  (easy/medium/hard), прогон по расписанию, история метрик.
- Публичные метрики: время до первого доступа, полнота цепочки, цена прогона
  в токенах/$ — против прошлых версий и (где возможно) против DSH-трейсов.

## Архитектура контура

```
 задача ──► координатор (чат/оркестратор)
              │  события (fact.confirmed, gate.passed, stall, …)
              ▼
   ┌─────────────────────────────────────────────┐
   │                blackboard                    │
   │  граф знаний · гипотезы · находки · лут      │
   └──▲───────────▲──────────────▲───────────────┘
      │           │              │
 стратег (вектора, исследователь  исполнители (рои,
 kill chain,      (CVE/техники →  swarm по задачам,
 вероятности)     гипотезы)       scope guard)
      │           │              │
      └───────────┴──► судьи (цель, валидация, скоуп) ◄── оператор
```

Граница авторизации (скоуп) и подтверждения — всегда между моделью и
действием; специалисты только предлагают. Это то, что отличает харнесс от
«агента с шеллом».
