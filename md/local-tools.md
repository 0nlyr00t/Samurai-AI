# Локальные инструменты: возможности, установка, границы

Samurai работает не только через Docker и релей: на машине оператора он берёт
уже установленные инструменты нативно, а отсутствующий — предлагает поставить
по проверенному рецепту. Релей остаётся запасным транспортом, не заменой.

Модель при этом не пишет ни одной install-команды. Она называет `tool_id`;
пакет, менеджер, argv, привилегии и healthcheck берутся из каталога рецептов.

## Что можно спросить у машины

```bash
samurai tool capabilities          # что здесь есть, read-only
samurai tool capabilities --json
```

Выводит ОС/дистрибутив/архитектуру, наличие `apt`/`brew`/Docker и его демона,
`sudo -n`, GPU, свободное место, найденные бинари с путями и версиями. Ничего не
устанавливает, не тянет образы и не повышает права. Один сломанный проб не
скрывает остальные.

## Порядок выбора пути

`native` → `project-local` → `pinned container` → `provision` (с approval) →
отказ с ручной командой. Причины машинные: `installed`,
`missing-binary`, `unsupported-platform`, `missing-privilege`,
`docker-unavailable`, `offline`, `manual-only`, `conflict`.

Native предпочтителен там, где важны железо и состояние (GPU, устройства);
контейнер — где нужна изоляция. `http.fetch` остаётся за брокером: он
пиннит DNS и перепроверяет redirect, а нативный curl этого не делает.

## Установка

```bash
samurai tool provision scan.nmap --dry-run   # только план
samurai tool provision scan.nmap             # план → approval → install → healthcheck
samurai tool verify scan.nmap                # read-only проверка
```

Dry-run печатает платформу, пакет, точные команды, требование привилегий и
healthcheck, и **ничего** не меняет: ни файлов, ни статусов, ни образов.

Исполнение — только argv без shell, только из рецепта. Состояния:
`planned → awaiting-approval → installing → verifying → ready | failed`.
Успешный exit ещё не успех: инструмент помечается готовым лишь после
healthcheck. Частично установленный пакет остаётся `failed`.

Правила:

- повторный provision уже работающего инструмента — no-op (только healthcheck);
- параллельная установка того же инструмента блокируется замком (в том числе
  между запусками — состояние лежит на диске);
- после `failed` новый запуск нужен явно, автоматических retry нет;
- офлайн запрещает установку целиком;
- `apt upgrade`, `brew upgrade` и удаление пакетов не выполняются.

## Привилегии

Обычные запуски и проектные установки — от текущего пользователя. Привилегии
только через фиксированный рецепт и `sudo -n`: пароль не запрашивается и через
модель не передаётся. Нет беспарольного sudo — отказ `missing-privilege` с
ручной командой для оператора.

Approval на установку отдельный от approval на запуск инструмента. YOLO
разрешает запуски, но системные изменения всё равно показывает.

## Каталог

Встроенные рецепты — проектное достояние в `assets/recipes` (nmap, ffuf,
nuclei, curl, hashcat, project-local `web.http-headers`). Свой рецепт ставится
через ту же границу доверия, что и манифест:

```bash
samurai tool install my-recipe.json --trusted
```

Для пакетов apt/brew репозитории текучие: рецепт помечает это
(`reproducible: false`), а установленная версия записывается в состояние, а не
обещается. Точная воспроизводимость только у project-local (файл + sha256).

## Из прогона

Команда агента `request_tool_provision {"tool_id": …}` (в чате — инструмент
`provision_tool`) уместна, когда `request_tool_run` ответил, что бинаря нет.
Отказ scope, неверный параметр, timeout и недоступная цель установки не требуют.
На один инструмент — одна попытка за прогон; после успеха модель запускает
инструмент заново, после повторного провала ветка закрывается с причиной.

## Что не входит

Metasploit, интерактивные оболочки, PTY и произвольные привилегированные
инструменты — отдельный stateful-дизайн. Автоустановка «всего Kali», удаление
пакетов и обновление ОС — тоже вне этой волны.
